【ミッション: 二重生成ロジックの統合とE2Eテスト (Epic 0 / ステップ2)】
アプリ本体の非同期ワーカーに対し、バッチ工場で確立した「GeminiとローカルLLMの二重生成ロジック」を移植し、ローカルDB（SQLite）と結合した上で、システム全体のE2Eテストを実行してください。

【絶対制約: DBトランザクションとLLM推論の分離】
LLMの推論（数秒〜数十秒）を待機している間、絶対にDBのロックやトランザクション（セッション）を保持し続けないこと。
必ず「DBのステータスを『処理中(processing)』に更新して一旦DBのコネクション/セッションを閉じる・手放す」→「LLMの推論を実行する」→「完了後、再度DBに接続して結果を書き込む」という非同期フローを厳守してください。

Step 1: アプリ本体ワーカーへの二重生成ロジックの移植
apps/evaluator/backend/services/generation.py などのアプリ側非同期ワーカー処理を確認し、以下の対応を行ってください。
・フロントエンドからのリクエストに基づき、GeminiとローカルLLM（Gemma/LocalUnsloth等）の両方でなぞかけを生成し、GeminiEvaluatorで評価するロジックを統合すること。
・VRAM枯渇を防ぐため、ローカルLLMの推論呼び出し部分は asyncio.Semaphore(1) などのグローバルセマフォで確実に囲み、複数リクエストが来ても直列で推論されるよう排他制御すること。

Step 2: ローカルDB（SQLite）との結合
アプリ側のワーカーも、Firestoreではなく新設した packages/shared_core/nazokake_core/database.py の Serialized Writer（同期/非同期ブリッジ）を用いてデータの読み書き・ステータス更新を行うようにリファクタリングしてください。

Step 3: 静的解析と全体E2Eテストの実行
修正後、uv run ruff check --fix を実行して構文をクリーンに保ってください。
フロントエンド（またはAPIのモックリクエスト）を起点とし、FastAPIでの受付 → ローカルDBへの「未処理」書き込み → ワーカーによる二重生成と評価（セマフォ制御付き） → ローカルDBの「完了」更新までの一連のバケツリレーが、ローカル環境で競合やフリーズなく完走することを実証するE2Eテストを実行し、その結果（ログ）を報告してください。
